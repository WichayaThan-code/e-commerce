# OMS Product Vision

บันทึกตำแหน่งธุรกิจตามที่ทีมกำหนดวันที่ 2026-09-19 ใช้เป็นหลักอ้างอิงเวลาออกแบบฟีเจอร์และตัดสินใจ scope ไม่ใช่ backlog พร้อมทำ — งานจริงยังต้องแตกเข้า 01-Task-Project-Tracking และให้ทีมตกลง priority/due อีกครั้ง

## ตำแหน่งธุรกิจ

เราขาย **ระบบ (OMS)** เป็นสินค้าหลัก ไม่ได้สร้างแพลตฟอร์มมาแข่งกับ Shopee, TikTok Shop หรือมาร์เก็ตเพลสอื่น จุดแข็งของทีมคือความเชี่ยวชาญด้านระบบ ไม่ใช่การสร้างฐานผู้ซื้อ

พระเอกของโปรดักต์คือ **OMS (Order Management System)** — หน้าร้าน (storefront) เป็นเพียงหนึ่งช่องทางป้อนออเดอร์เข้า OMS สำหรับร้านที่ยังไม่มีที่ขาย ไม่ใช่ตัวสินค้าหลัก

## กลุ่มเป้าหมาย

| กลุ่ม | สถานการณ์ปัจจุบัน | Pain point | สิ่งที่เราขายให้ |
| --- | --- | --- | --- |
| A. ไม่มีแพลตฟอร์ม | ขายผ่าน DM / โซเชียล จดออเดอร์มือ | ไม่มีหน้าร้านเป็นทางการ ไม่อยากเช่าที่บนแพลตฟอร์มอื่น | ลิงก์หน้าร้าน (storefront) ใช้แทนการ DM/จดออเดอร์มือ ผูกเข้า OMS เดียวกัน |
| B. ขายดีอยู่แล้วหลายแพลตฟอร์ม | ขายบน Shopee, TikTok, Lazada ฯลฯ พร้อมกัน | ต้องสลับเข้าหลังบ้านทีละแพลตฟอร์มเพื่อดูออเดอร์ ทำรายงาน ปริ้น label | OMS ที่ manage ทุกช่องทางจากศูนย์กลางเดียว |

กลุ่ม B คือกลุ่มที่ระบบสร้างมูลค่าชัดที่สุด และเป็นเหตุผลหลักที่ลูกค้าจะเลือกใช้ เพราะเจ็บปวดจากการจัดการหลายหลังบ้านอยู่แล้วจริง

ทีมตกลงเริ่ม Phase 1 จากกลุ่ม A ก่อน (2026-09-19) เพราะเป็นกลุ่มที่ยังไม่มีหน้าร้านเลย เห็นคุณค่าได้เร็วที่สุด — รายละเอียดอยู่ที่หัวข้อ "Phase 1" ด้านล่าง

## โมเดลการเงิน (Payment)

**ตัดสินใจ (2026-09-19): ร้านต่อ payment gateway ของตัวเอง เราไม่แตะเงินลูกค้า**

- เราไม่รับเงินแทนร้าน ไม่ทำ escrow/พักเงิน ไม่หัก commission จากยอดขาย และไม่ทำ settlement/โอนเงินให้ร้าน
- แต่ละร้านเชื่อมต่อ payment gateway ของตัวเอง (เช่น Omise, 2C2P, หรือของธนาคารที่ร้านมีอยู่แล้ว) เงินไหลจากลูกค้าเข้าร้านโดยตรง
- โมเดลนี้สอดคล้องกับตำแหน่งธุรกิจ "ขายระบบ" — เราไม่ใช่ตัวกลางทางการเงิน จึงไม่ต้องแบกภาระ compliance/ใบอนุญาตด้านการเงินที่มาพร้อมการถือเงินลูกค้า

**หมายเหตุ:** สื่อการตลาด/ไดอะแกรมเก่าที่อธิบายว่า ThaiShopFun เป็น "Marketplace Commerce Platform" พร้อม Buyer Protection (พักเงิน), Split Payment (หัก Platform Commission), Settlement (หักค่าคอมแล้วโอนให้ผู้ขาย) — โมเดลนั้น **ถูกแทนที่แล้ว** ด้วยการตัดสินใจข้างต้น ห้ามใช้สื่อชุดนั้นอ้างอิงสถาปัตยกรรมการเงินอีก

## Phase 1: กลุ่ม A — หน้าร้าน (Storefront)

Phase แรกที่ทีมตกลงเริ่มทำ (2026-09-19) เป้าหมายคือแทนที่การขายผ่าน DM/Line ด้วยหน้าร้านที่ใช้งานสะดวกทั้งฝั่งร้านและฝั่งลูกค้า

**ฝั่งร้านค้า (merchant)**

- สมัคร/ตั้งค่าแล้วได้ลิงก์ร้านของตัวเอง 1 ลิงก์ ใช้แทนการโพสต์ขายบน Facebook เพื่อรับ DM
- ลงสินค้าเอง: รูป ราคา รายละเอียด และจัดหมวดหมู่สินค้าภายในร้าน
- ออเดอร์ที่เข้ามาทางหน้าร้านนี้ ไหลเข้า OMS เดียวกับช่องทางอื่นของร้าน (สอดคล้องกับ Order Aggregation)

**ฝั่งลูกค้า (buyer) — โจทย์ความสะดวกข้ามร้าน**

ลูกค้าไม่ควรต้องสมัครสมาชิก/login ใหม่ทุกครั้งที่เข้าร้านที่ต่างกัน จึงต้องมี:

- บัญชีผู้ซื้อกลางบัญชีเดียว ใช้ล็อกอินได้กับทุกร้านที่อยู่บนระบบเรา (สมัครครั้งเดียว ไม่ต้องสมัครซ้ำต่อร้าน)
- หน้ากลาง (hub/directory) ที่รวมรายชื่อร้านค้าทั้งหมด จัดหมวดหมู่ว่าแต่ละร้านขายอะไร (แนวทางคล้าย Grab ที่จัดกลุ่มร้านตามประเภท) ให้ลูกค้าเลือกเข้าไปยังร้านที่สนใจ
- จากหน้ากลาง กดเข้าร้าน → ดูสินค้า → ใส่ตะกร้า → checkout ได้โดยไม่ต้องออกจากระบบไปสมัครใหม่

**ข้อควรระวัง:** หน้ากลางนี้เป็น "ไดเรกทอรีเพื่อความสะดวกของผู้ซื้อ" ไม่ใช่มาร์เก็ตเพลสที่เราคัดสรร/โปรโมทร้านแข่งกันเอง หรือเก็บค่าคอมจากการขาย (ดู "โมเดลการเงิน" ด้านบน) — ยังต้องตัดสินใจเพิ่มว่า checkout จะเป็นตะกร้าต่อร้าน (แยกตาม payment gateway ของแต่ละร้าน) หรือมีขั้นตอนอื่น เพราะร้านแต่ละร้านต่อ gateway ของตัวเอง เงินไม่ได้รวมศูนย์

## ไม่ทำ (Non-goals)

- ไม่สร้างหน้ามาร์เก็ตเพลสกลางที่คัดสรร/โปรโมทร้านแข่งกันเองแบบ Shopee/TikTok หรือเก็บค่าคอมจากยอดขาย (ต่างจาก merchant-onboarding แบบเดิมที่ตั้งใจให้ร้านค้าสมัครเข้ามาขายในแพลตฟอร์มเราแบบมีค่าคอม)
- ไม่แข่งสร้างฐานผู้ซื้อ/ทราฟฟิกกับ Shopee, TikTok หรือแพลตฟอร์มอื่น
- ไม่ล็อกลูกค้าให้ขายผ่านช่องทางเราเท่านั้น — OMS ต้องอยู่ร่วมกับช่องทางที่ลูกค้ามีอยู่แล้วได้
- ไม่รับเงินแทนร้าน ไม่ทำ escrow/split payment/settlement (ดู "โมเดลการเงิน")

## ผลต่อโค้ดปัจจุบัน

โค้ดตอนนี้ (merchant application, storefront, admin approval) เขียนตามโครงมาร์เก็ตเพลสเดิมก่อนปรับตำแหน่งธุรกิจ ยังใช้ต่อได้เพราะ:

- ระบบสมาชิก/สิทธิ์ (auth) และการเก็บข้อมูลร้านค้า (merchant application) ยังจำเป็นสำหรับทั้งสองกลุ่ม
- หน้าร้าน (storefront) ที่มีอยู่ตอบโจทย์กลุ่ม A ได้โดยตรง เพียงต้องปรับกรอบความคิดจาก "ร้านสมัครเข้ามาขายในตลาดกลางของเรา" เป็น "ร้านมีหน้าร้านของตัวเองที่เราจัดให้"

ส่วนที่ยังไม่มีในโค้ดและเป็นแกนของ OMS จริง ๆ (ยังไม่ได้แตกเป็น task): การเชื่อมต่อ/ดึงออเดอร์จากแพลตฟอร์มภายนอก (Shopee/TikTok API เป็นต้น), การรวมออเดอร์หลายช่องทางในตารางเดียว, reporting ข้ามช่องทาง, การเชื่อม ads API, และการปริ้น label ผ่านผู้ให้บริการขนส่งหลายเจ้า

## ขั้นถัดไปที่แนะนำ

1. ออกแบบบัญชีผู้ซื้อกลาง (buyer account เดียวใช้ได้ทุกร้าน) และหน้า hub/directory รวมร้านค้า ตามที่ระบุใน Phase 1
2. ออกแบบ data model ออเดอร์ให้รองรับหลายช่องทางตั้งแต่ต้น (channel เป็น field ของ order ไม่ใช่สมมติว่ามีช่องทางเดียว) เผื่อไว้สำหรับกลุ่ม B ในเฟสถัดไป
3. ตัดสินใจ flow checkout เมื่อแต่ละร้านต่อ payment gateway ของตัวเอง (ตะกร้าต่อร้าน vs. อื่น ๆ)
4. แตกฟีเจอร์ Phase 1 (storefront, buyer account, hub) เป็น PRJ/TASK ใน 01-Task-Project-Tracking ก่อน แล้วค่อยแตกของกลุ่ม B (order aggregation ข้ามแพลตฟอร์ม, Shopee/TikTok API) ในเฟสถัดไป
